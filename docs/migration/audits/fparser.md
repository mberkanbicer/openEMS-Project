# fparser Audit

**Audit status:** Source/API audit complete for the pinned revision; rule-level
optimizer equivalence, broader backend compatibility, installation packaging,
and cross-platform runtime checks remain unresolved. The initial `fparser-rs`
implementation is tracked separately in `fparser/rust/`; this audit remains
the original-source behavior record.

## Scope and evidence

Inspected the pinned fparser revision
`4b9c845b449b520c4b8c5f23c74cd04820084f81`, inventoried all 25 tracked paths,
and reviewed the public header, core parse/evaluation paths, opcode/type
declarations, numeric helper references, generated identifier/opcode includes,
build definitions, documentation, examples, optional numeric wrapper headers,
and CI configuration. Detailed optimizer rewrite rules and optional backend
internals remain outstanding.

The original fparser CMake target configured and built successfully on this
Windows host with Visual Studio 2022/MSVC 19.44, producing
`fparser.dll`. The example program was also compiled and run with `x^2` over
`x = -1, 0, 1`, producing `1, 0, 1`. The build under `%TEMP%` emitted
MSBuild temporary-directory/output-path warnings; compiling the example
emitted narrowing-conversion warnings in generated `fpoptimizer.cc`. No
compile failure occurred. The repository contains examples but no registered
CTest or other test suite. A second compile enabled float, long double, and
long integer variants and ran `example2.cc`: the floating variants preserved
their distinct outputs, while Windows `long double` matched `double` output
and integer `x*x` produced `0, 1, 4`. These are smoke cases, not a full
semantic baseline. A separate complex-double configuration was also compiled;
all three complex scalar configurations compiled and ran. MPFR and GMP
configurations were not included in that initial build.
Additional default-double smoke probes evaluated `sin(x)` at 0, 1.5, and 3
as `0`, `0.997495`, and `0.14112`, and evaluated a constant sum of ten `0.1`
terms compared with 1 as true (`1`). These single examples do not establish
trigonometric or epsilon-comparison coverage.
A temporary C++ probe linked the original `fparser.cc` and `fpoptimizer.cc`
and confirmed evaluation error codes 1-4, nested-parser error propagation,
inline-variable stack fetches, conditional branch skipping, and optimizer
effects on user callbacks. Exact outputs are recorded below; they remain
focused compatibility probes, not a comprehensive baseline. A separate
semantic probe confirmed operator/unit precedence, degree conversion,
absolute-epsilon boundaries, and the logical truth threshold.

## Public API and behavior map

- `Parse` validates the variable list, parses the expression, and compiles it
  into bytecode. It returns `-1` on success or a source offset on failure;
  `ErrorMsg` and `GetParseErrorType` expose the parse failure.
- `ParseAndDeduceVariables` repeatedly discovers unknown identifiers and
  returns the variable list. `setDelimiterChar` supports parsing a terminated
  expression prefix.
- `Eval` runs the bytecode interpreter using a value stack. It returns zero
  after a detected evaluation error; callers must inspect `EvalError`.
- Evaluator error codes are 1 for division/modulo by zero, 2 for a negative
  real square root, 3 for invalid logarithm or zero-to-negative power, and 4
  for invalid inverse trigonometric input. Nested parser calls propagate the
  child parser's evaluation error.
- `AddConstant`, `AddUnit`, callback-based `AddFunction`, parser-based
  `AddFunction`, and wrapper-based registration extend the shared identifier
  namespace. `RemoveIdentifier` cannot remove variables. Parser links are
  checked for recursive cycles.
- Parser-based `AddFunction` stores a non-owning pointer and snapshots the
  linked parser's variable count. The documentation requires the linked parser
  to outlive its caller and its variable count to remain unchanged. Function
  wrappers, in contrast, are copied and reference-counted; copies of a parser
  share wrapper state. Raw C++ callbacks are stored as non-owning function
  pointers.
- Inline variables are compiler-time names mapped to evaluation-stack slots;
  repeated uses emit duplicate/fetch opcodes rather than re-evaluating their
  definition.
- `Optimize` rewrites bytecode when optimizer support is compiled in; it is
  explicitly called and is not part of `Parse`. Documentation warns it can be
  slow and does not perform evaluation-time sanity checks.
- The generated optimizer's visible pipeline applies four named rewrite
  rounds, then a logical-rewrite grammar selected by
  `FP_ENABLE_SHORTCUT_LOGICAL_EVALUATION`. The rule payload is generated and
  heavily encoded in the only tracked optimizer source, so the individual
  transformations and their conditions have not yet been fully mapped.
- The optimizer source contains 262 generated rules and grammar subsets for
  recreate (22), ordinary rounds 1-4 (125, 103, 79, and 12), shortcut and
  non-shortcut logical evaluation (53 and 56), ignore-if-side-effects (59),
  and absolute-logical rewrites (9). These subsets overlap; their counts are
  not additive. Rule metadata supports logical-context and numeric-type
  restrictions plus immediate-value constraints for numeric class, sign,
  oneness, and constness. Before bytecode synthesis, the optimizer repeatedly
  applies the recreate grammar while recreating inversions and negations. The
  default optimization pipeline applies rounds 1-3, the
  non-shortcut logical grammar only when shortcut evaluation is disabled,
  round 4, shortcut logical rewrites when enabled, optional ignore-if-
  side-effects rewrites, and absolute-logical rewrites. This maps pipeline
  structure and guard categories, not every generated rule pattern.
- The optional MPFR wrapper uses a 256-bit default precision and MPFR calls
  rounded with `GMP_RNDN`; changing global precision rounds all allocated
  values and cached constants. Its API warns that constructing from `double`
  cannot recover precision absent from the original 53-bit value, so decimal
  literals should use `parseValue`.
- The optional GMP integer wrapper uses GMP `mpz_t` values with a 256-bit
  initial allocation default. Its `long double` constructor converts through
  `double`, and the type-specific helper functions implement many
  transcendental operations as zero. Both optional wrappers return strings
  through shared internal buffers. Their source files are outside the CMake
  target and require the external MPFR/GMP headers and libraries. Runtime
  probes later succeeded under WSL with the preinstalled headers/libraries:
  the MPFR parser evaluated `x*x+1` at 128-bit precision for `x=0.1`, and the
  GMP parser returned the exact integer result `15241578750190522` for
  `x*x+1` at `x=123456789`. No dependency was installed. The MPFR build emits
  a deprecation warning for `mpfr_root`; broader wrapper behavior and install
  packaging remain unverified.
- Copy/assignment uses copy-on-write. The default evaluator stack is stored in
  parser state, so concurrent `Eval` calls on one instance are not thread-safe.
  Compile-time options allocate a per-call stack; the documentation says
  MPFR/GMP variants cannot use that thread-safe mode.
- Floating comparison operators use type-specific epsilon values. The inspected
  defaults include `1e-12` for double, `1e-5` for float, and `1e-14` for long
  double.
- The documented grammar includes units, exponentiation, unary minus/not,
  arithmetic/modulo, epsilon comparisons, logical `&`/`|`, and the `if`
  expression. Units bind to the preceding element. `useDegrees` changes
  trigonometric angle handling. Inline variables, custom functions, and
  multiple numeric types are also public behavior.
- Built-in functions are defined by the ordered `Functions[]`/`OPCODE` tables,
  with type and angle flags, and implemented through type-specific math
  wrappers. The complete source-listed set is `abs`, `acos`, `acosh`, `arg`,
  `asin`, `asinh`, `atan`, `atan2`, `atanh`, `cbrt`, `ceil`, `conj`, `cos`,
  `cosh`, `cot`, `csc`, `exp`, `exp2`, `floor`, `hypot`, `if`, `imag`, `int`,
  `log`, `log10`, `log2`, `max`, `min`, `polar`, `pow`, `real`, `sec`, `sin`,
  `sinh`, `sqrt`, `tan`, `tanh`, and `trunc`. The table flags `abs`, `if`,
  `max`, and `min` as supported for integer types; `arg`, `conj`, `imag`,
  `polar`, and `real` are complex-only. Angle-input flags are set for `cos`,
  `cosh`, `cot`, `csc`, `polar`, `sec`, `sin`, `sinh`, `tan`, and `tanh`;
  angle-output flags are set for `acos`, `acosh`, `arg`, `asin`, `asinh`,
  `atan`, and `atan2`. These are source-level classifications; the full
  function/type cross-product has not been runtime-tested. The opcode/name
  tables must remain aligned.

## Findings and migration risks

1. **Documentation mismatch, confirmed; runtime impact not asserted.** The
   v4.5 release notes say `eval()` was removed, and the source opcode/name
   tables contain no `eval` function, but the function table and `EvalError`
   documentation still describe `eval()` and recursion error 5. Do not port
   `eval()` based only on those stale sections; resolve the public compatibility
   contract before migration.
2. **Optimizer observability.** Default configuration enables the optimizer
   and shortcut logical rewrites, while documentation says optimization may
   change whether both logical operands are evaluated. Custom functions can
   have side effects, so differential tests must cover optimized and
   unoptimized behavior. A focused probe confirmed `0*count(x)` called the
   callback once before optimization and zero times afterward; `0&count(x)`
   likewise called it once before and zero times after optimization. This
   matches the documented assumption that callbacks are pure, but is
   observable behavior that a replacement must characterize. A broader sample
   matched optimized and unoptimized outputs for trigonometric identity,
   conditional square roots, `log(exp(x))`, a quadratic, and `x^0`. It also
   changed `0*log(x)` at `x=-2` from evaluation error 3 to zero with no error.
   The unoptimized parse of `x/x` already returned 1 at `x=0`, indicating a
   compile-time rewrite before explicit `Optimize()`.
3. **Configuration is part of behavior.** The default build uses `double`;
   float, long double, integer, MPFR, GMP, and complex variants are guarded by
   compile-time flags. Float, long double, and long integer were enabled in a
   manual example build; complex double, float, and long double all compiled
   and ran. Separate C++98 MPFR and GMP builds also compiled and passed focused
   arithmetic probes under WSL. Integral variants have a reduced
   grammar. The CMake target does not enable those variants or compile the
   MPFR/GMP sources. The `long`-based parser also inherits platform-dependent
   `long` width.
4. **Potential packaging boundary to verify.** Optional MPFR/GMP headers and
   sources exist, but the inspected CMake install rule installs only
   `fparser.hh`. Whether this is intentional for this fork is unresolved.
5. **Optional numeric types are not interchangeable.** MPFR input
    construction, global precision changes, rounding, and string conversion
    need independent compatibility cases. GMP integer transcendental helpers
    return zero and conversions can pass through native floating-point types;
    these semantics must not be mistaken for arbitrary-precision real math.
6. **Reference tests are missing.** CI builds the library across platforms but
    no unit-test/CTest suite is present. Executed examples cover basic `x^2`,
    representative scalar types, three sine samples, and one constant equality
    expression; separate focused probes cover only a handful of errors and
    stateful cases. The successful Windows build and smoke output do not
    validate the full expression semantics.
7. **Evaluation error state after parse failure.** In a probe, evaluating
   `1/0` returned zero with `EvalError()==1`; after parsing invalid `x+`,
   `Eval()` again returned zero but `EvalError()` remained 1. Source confirms
   the parse-error early return happens before the evaluator clears or sets
   this state. The behavior is observed, not classified as a defect; record it
   as an API edge case and clarify compatibility expectations.
8. **Function-wrapper registration leaks on failure.** In `fparser.hh:220-221`,
   the API allocates a copied wrapper with `new DerivedWrapper(wrapper)` before
   calling `addFunctionWrapperPtr`. In `fparser.cc:985-992`, that helper
   returns false when `AddFunction` rejects the name (for example, because it
   duplicates a built-in), without deleting the newly allocated wrapper. A
   failed registration therefore leaks the copied wrapper. The root repository
   does not own this submodule implementation; record the finding for the
   fparser repository rather than changing its source here.

## Remaining audit work

- Review the generated optimizer rewrite rules and confirm conditions under
  which transformations preserve errors, side effects, and floating behavior.
  The current differential corpus is representative only; it does not verify
  each generated rewrite rule.
- Establish reference cases for precision/rounding, comparison boundaries,
  units, degree conversion, precedence, and supported-function edge behavior.
- Expand MPFR and GMP reference cases beyond the initial arithmetic probes,
  including precision/conversion behavior and installation packaging.
- Characterize complex branch-cut/signed-zero behavior across compilers and
  compare optimizer effects beyond the tested square-root expression.
- Expand original behavior cases for the full supported-function/type
  cross-product, numeric edge cases, and custom functions. Representative
  behavior is recorded, but there is currently no golden-output set and the
  generated optimizer rules have not been verified one-by-one.
- Resolve the stale `eval()` documentation during the full audit; this is not a
  request to change upstream code or its submodule pointer.
